# Pal Buddy Guy: 애니팔의 가장 친한 친구
Vive Pro Eye와 Vive Facial Tracker의 트래킹을 개선하는 프로젝트입니다. 표정을 짓고 녹화한 뒤 작은 신경망을 학습시키면, 그 표정으로 VRCFaceTracking 파라미터를 움직일 수 있습니다.

이제 GUI가 있고, 데이터 수신·녹화·학습·보정·출력을 프로그램 하나에서 모두 처리합니다.

> English: [README.md](README.md)

# 시스템 요구 사항
* CUDA를 지원하는 NVIDIA GPU(VRAM 4GB 이상)를 권장합니다. CPU(와 Apple MPS)에서도 동작하지만 학습이 느립니다.
* **두 트래커 모두, 페이셜 트래커만, 또는 Pro Eye만** 있어도 동작합니다. 아래 *입력 방식*을 참고하세요.
* Python 3.8 이상과 PyTorch.

# 설치
1. SRanipal 안의 tvm runtime을 교체합니다. `tvm runtime` 폴더의 .DLL 파일 두 개를 `C:\Program Files\VIVE\SRanipal`에 복사해 기존 파일을 덮어씁니다. 되돌릴 때를 대비해 기존 파일은 먼저 백업해 두세요.
2. **`PalBuddyGuy.bat`을 더블클릭합니다.** 이게 전부입니다.

처음 실행할 때 런처가 하는 일:
* Python 3.9 이상을 찾고, 없으면 winget으로 설치할지 묻습니다.
* `.venv` 폴더에 전용 환경을 만듭니다. 시스템 Python은 건드리지 않습니다.
* PyTorch(NVIDIA GPU가 있으면 CUDA 버전, 없으면 CPU 버전)와 나머지 패키지를 설치합니다. 다운로드가 2~3GB라 몇 분 걸립니다.
* 바탕화면에 **Pal Buddy Guy** 바로가기를 만들지 묻습니다.

그다음부터는 .bat이나 바로가기를 더블클릭하면 콘솔 창 없이 바로 GUI가 열립니다. 시작 오류(예: 포트가 이미 사용 중)는 대화 상자로 표시되고, 모든 기록은 `palbuddy.log`에 남습니다. 처음부터 다시 설치하려면 `.venv` 폴더를 지우고 .bat을 다시 실행하세요.

# 실행
Pal Buddy Guy를 **SRanipalRuntime보다 먼저** 실행하고 (더블클릭), 그다음 **VRCFaceTracking**을 실행하세요.

SRanipal은 어떤 앱이 사용할 때만 카메라를 켜고, 그때 Pal Buddy Guy가 읽는 신경망도 함께 돌아갑니다. 트레이 아이콘이 초록색으로 바뀌는 게 그 표시입니다. Pal Buddy Guy는 SRanipal API를 직접 쓰지 않으므로, VRCFaceTracking을 켜기 전까지는 아이콘이 회색이고 트래커 데이터가 들어오지 않습니다. 그동안 앱에 안내 문구가 표시됩니다. 녹화와 트래킹에는 VRCFaceTracking이 켜져 있어야 하고, 학습에는 필요 없습니다.

창은 **간단 모드**로 시작합니다. 녹화, 학습, 트래킹에 필요한 것만 보입니다. 오른쪽 위 **고급 설정**을 체크하면 나머지가 모두 나타납니다: 학습 옵션과 모델 비교, 클래스별 민감도, 부드러움, 병합 파라미터, 클래스별 OSC, 포트, 추론 성능. 숨긴 설정은 값이 그대로 유지되고 계속 적용됩니다. 모드를 바꿔도 설정은 바뀌지 않습니다.

직접 만든 Python 환경에서 수동으로 실행하는 방법 (고급):

```
pip install -r requirements.txt   # 먼저 GPU용 torch를 설치하세요: https://pytorch.org/get-started/locally/
python -m palbuddy          # GUI  (python script.py 와 같음)
python -m palbuddy --cli    # 예전 스크립트처럼 텍스트 명령으로 사용
python -m palbuddy --infer  # 바로 트래킹 시작
```
.bat에 준 인자도 그대로 전달됩니다. 예: `PalBuddyGuy.bat --infer`

앱이 SRanipal 스트림을 직접 받기 때문에 이제 `tvm_proxy.py`를 따로 실행할 필요가 없습니다. 별도 프록시가 필요하면 아래 *레거시 프록시 모드*를 참고하세요.

모든 설정은 처음 실행할 때 만들어지는 `config.json`에 저장됩니다. GUI에서 바꿀 수 있고, 소스 코드를 고칠 필요는 없습니다.

## 1. 스트림 확인 (실시간 탭)
상태 표시줄에 아이 트래커, 페이셜 트래커, VRCFaceTracking의 연결 상태와 프레임 속도가 표시됩니다.
카메라 미리보기에는 **위에 눈, 아래에 얼굴**이 보여야 합니다. 반대로 보이면 **눈/얼굴 뒤바꾸기**를 누르세요. 선택은 저장됩니다.

### 입력 방식
실시간 탭의 **입력 방식** 칸에서 신경망에 넣을 트래커를 고릅니다.

| 입력 방식 | 사용하는 데이터 |
|---|---|
| 눈 + 입 (두 트래커) | 두 트래커의 특징값 모두 (원래 동작) |
| 입만 (페이셜 트래커) | 페이셜 트래커의 특징값만 |
| 눈만 (Pro Eye) | Pro Eye의 특징값만 |

* 연결된 트래커가 선택한 방식과 맞지 않으면 안내가 뜹니다. 트래커가 하나만 들어오면 미리보기를 보고 *입만* 또는 *눈만*을 누르세요. 트래커가 하나일 때는 스트림이 SRanipal의 어느 포트로 들어오든 상관없어서 뒤바꾸기가 필요 없습니다.
* 모델은 학습한 입력 방식에서만 동작하고, 입력 방식은 모델 파일에 저장됩니다. 방식을 바꾸면 다시 학습하세요.
* 녹화 파일에는 항상 두 트래커 데이터가 모두 저장되고, 없는 트래커는 0으로 채워집니다. 그래서 **두 트래커로 녹화한 파일은 입만/눈만 학습에도 다시 쓸 수 있습니다.** 트래커 하나로 녹화한 파일은 다른 트래커가 필요한 방식에는 쓸 수 없고, 학습할 때 어느 파일이 문제인지 알려 줍니다.
* 어느 방식이든 출력은 VRCFT의 *입* 모양 파라미터를 움직입니다. VRCFT 모듈이 받는 형식이 그것이기 때문입니다. 일반 아이 트래킹(시선, 깜빡임)은 전처럼 그대로 동작합니다. 눈만 모드에서도 눈 카메라로 보이는 찡그림 같은 표정을 학습해서 입 모양 파라미터에 연결할 수 있습니다.

## 2. 녹화 (녹화 탭)
이름을 입력하고 **녹화**를 누릅니다. 카운트다운이 끝나면 2048프레임(약 30초)을 녹화해서 `<데이터셋 폴더>/<이름>-em.mmap`에 바로 저장합니다.
* **neutral**(무표정) 녹화는 *반드시* 있어야 합니다. 완전한 무표정일 필요는 없습니다. 말하기, 두리번거리기, 깜빡이기처럼 트래킹하고 **싶지 않은** 얼굴을 담아야 합니다. 그래야 신경망이 무엇에 반응하지 *말아야* 하는지 배웁니다.
* 녹화하는 동안 목표 표정은 계속 유지하되 조금씩 움직이세요 (헤드셋을 고쳐 쓰거나 고개를 돌리는 등). 목표 표정만 일정하고 나머지는 다양한 데이터가 좋습니다.
* 녹화 파일 하나가 약 200MB(float16)이므로, 설정 탭에서 데이터셋 폴더를 여유 공간이 있는 드라이브로 지정하세요. 이전에 만든 약 400MB(float32) 녹화도 그대로 불러옵니다. float32로 다시 녹화하려면 `config.json`에서 `"record_float16": false`로 설정하세요.
* 예전 `.pkl` 녹화 파일은 **예전 .pkl 변환**으로 변환할 수 있습니다.

## 3. 클래스 설정과 학습 (학습 탭)
클래스 하나가 신경망 출력 하나입니다. **첫 번째 클래스는 neutral이어야 합니다.** 클래스마다 녹화 파일과, 필요하면 움직일 SRanipal 입 모양("대상 파라미터")을 고릅니다. 녹화 탭에서 파일을 고르고 **클래스에 추가…**를 눌러도 됩니다.
**학습 시작**을 누르면 모든 클래스가 한 모델로 한꺼번에 학습됩니다. 학습이 끝날 무렵 손실 곡선이 0.001 선 아래로 내려가야 합니다. 그렇지 않으면 녹화 파일이나 클래스 목록에 문제가 있는 것입니다. 그다음 **모델 저장**을 누르세요.

## 4. 트래킹과 보정 (실시간 탭)
**트래킹 시작**을 누릅니다. 각 출력은 원시값과 VRCFT로 보내는 값으로 표시됩니다.
**빠른 보정 (FastCal)**은 아바타에 표정을 하나씩 차례로 지어 보여 줍니다. 얼굴로 따라 하세요. 측정한 세기가 각 클래스의 *최대값*이 되고, 학습 탭에서 직접 고칠 수도 있습니다. FastCal은 대상 파라미터가 지정된 클래스만 보정합니다. OSC 출력만 쓰는 클래스는 아래 *민감도*의 **자동 (5초)**을 쓰세요. **스무딩**은 약간의 지연을 감수하고 떨림을 줄입니다.

## 5. 추론 성능 (설정 탭 → 추론 성능)
트래킹은 새 프레임마다, 즉 1초에 약 60번 신경망을 실행합니다. 아래 설정으로 GPU, CPU, 메모리, 지연 시간 사이의 균형을 조절합니다.

| 설정 | 하는 일 |
|---|---|
| **추론 엔진** | *ONNX Runtime*이 CPU에서 가장 빠르고, 트래킹 중에 PyTorch를 불러오지 않아 RAM을 수백 MB 아낍니다. *자동*은 설치돼 있으면 이걸 쓰고, 런처가 설치해 줍니다. 모델을 저장하면 `.pt` 옆에 `.onnx` 사본(과 int8 버전)이 만들어지고, `.pt`가 더 새로우면 자동으로 갱신됩니다. |
| **실행 장치** | *CPU*(기본값)는 GPU를 VR에 온전히 양보합니다. int8 추론은 CPU 코어 하나의 약 1/3을 씁니다. *자동*은 GPU가 있으면 GPU를 씁니다. ONNX Runtime에서는 DirectML(`onnxruntime-directml`)을 뜻하고, NVIDIA, **AMD**, Intel GPU에서 모두 동작합니다. *GPU*는 GPU를 강제로 씁니다. |
| **CPU 스레드 수** | 기본값 1. 스레드를 늘리면 지연은 줄지만 전체 CPU 사용량은 **늘어납니다.** |
| **int8 양자화** | CPU에서 큰 선형 계층에 int8 가중치를 씁니다. 같은 모델 그대로, 재학습 없이 약 2~3배 빨라집니다. 출력 차이는 약 0.003입니다. |
| **최대 추론 빈도** | 예: 30Hz. 중간 프레임을 건너뛰어 작업량을 절반으로 줄입니다. 실시간 탭의 *스무딩*과 함께 쓰세요. |

**이 PC에서 비교 측정**은 사용 가능한 모든 방식을 현재 모델로 측정해서, 이 PC에 가장 잘 맞는 방식을 고를 수 있게 해 줍니다. 실시간 탭에는 사용 중인 방식, 프레임당 시간, 프로세스 전체 CPU 사용량이 표시됩니다.

### 모델 구조와 학습 방식 (학습 탭)
| 모델 | 가중치 | 연산량 | |
|---|---|---|---|
| *표준* | 2,700만 | 1.15억 곱셈-덧셈 | 원본 신경망 |
| *경량* | 360만 | 3,300만 | 구조는 같고 채널 수만 줄임 |
| *컴팩트* | 90만 | 1,100만 | 적은 데이터용: 입력 특징값을 채널별로 정규화(기준값은 녹화 데이터에서 계산해 모델에 저장), 1×1 conv로 128→64 채널 축소, 작은 출력부 |

표준 모델 가중치의 97%가 선형 계층 하나에 몰려 있는데, 몇 분 분량의 녹화에 비하면 지나치게 많습니다. 작은 모델은 과적합이 덜해서 빠를 뿐 아니라 *더 정확할* 수도 있습니다. 어느 쪽이 가장 좋은지는 녹화 데이터에 따라 다릅니다.

| 학습 방식 | |
|---|---|
| *MSE* (원본) | ReLU 출력을 원-핫 정답에 맞춰 학습합니다. 클래스끼리 서로 경쟁합니다. |
| *BCE* | 시그모이드 출력을 이진 교차 엔트로피로 학습합니다. 클래스마다 "이 표정이 보이는가"를 독립적으로 판단합니다. |

학습할 때마다 검증 구간에서 가장 성적이 좋았던 에폭의 가중치를 남기므로, 너무 오래 학습해도 손해가 없습니다.

### 가이드 녹화와 강도 학습 (녹화 / 학습 탭)
Project Babble 같은 블렌드셰이프 트래커는 "이건 표정 X"가 아니라 *연속적인* 정답(각 표정이 얼마나 강한지)으로 학습합니다. Pal Buddy Guy의 원래 녹화는 "이 파일 전체가 표정 X"라는 정보만 있어서, 모델 출력이 0과 1 사이를 오가고 녹화 시점의 차이를 표정 차이로 착각하기도 합니다. 이 차이를 줄이기 위해 두 가지를 추가했습니다.

* **가이드 녹화** (녹화 탭, 모든 표정에 권장, 약 36초): 초록 막대와 비프음(헤드셋을 쓴 채로 쓸 수 있게, Windows)이 표정을 얼마나 강하게 지을지 알려 줍니다. 소리 없음 = 무표정, 음이 높을수록 강하게. 최대까지 서서히 올리고, 유지하고, 무표정으로 돌아오고, 절반 강도까지 갔다 돌아오는 과정을 세 번 반복합니다. 프레임마다 강도가 정답으로 저장됩니다 (반응 시간을 고려해 0.3초 늦춰서, 녹화 파일 옆 `.labels.json`에 저장). 강도 *v*인 가이드 프레임은 *v* × 표정 + (1 − *v*) × 무표정으로 학습합니다. 가이드 녹화마다 같은 착용 상태의 무표정 구간이 들어 있어서, 모델이 녹화 시점으로 표정을 구분하지 못하게 됩니다.
* **중간 강도 학습 (mixup)** (학습 탭, 기본 켜짐): 표정 샘플의 절반을 무작위 무표정 프레임과 섞고(`x = λ·표정 + (1 − λ)·무표정`), 정답도 같은 비율로 섞습니다. 일반 녹화로도 중간 강도를 배울 수 있습니다.

한 클래스 안에서 가이드 녹화와 일반 녹화를 섞어 써도 됩니다. 검증 지표는 연속 정답을 쓰기 때문에, 비교 창의 *강도 오차*로 각 모델이 강도를 얼마나 잘 따라가는지 볼 수 있습니다.

### 스무딩 (실시간 탭)
*스무딩*은 Project Babble과 VRCFaceTracking이 쓰는 1-Euro 필터입니다. 작은 떨림은 강하게 잡고, 빠른 실제 움직임은 지연이 적게 통과시킵니다. 슬라이더 중간쯤이 Babble 기본값(min cutoff 약 3Hz, β 0.9)과 비슷합니다.

### 모델 비교 후 선택 (학습 탭)
**모델 비교 후 선택…**은 선택한 조합(기본: 표준/경량/컴팩트 × MSE/BCE)을 같은 녹화, 같은 샘플링으로 학습하고, 각각 검증 구간으로 채점한 뒤 현재 추론 설정으로 이 PC에서 속도를 잽니다. 결과 표의 항목은 다음과 같습니다.

| 항목 | 의미 |
|---|---|
| 정확도 | 보여 준 표정의 출력이 가장 높음 |
| 인식률 | 보여 준 표정의 출력이 0.5를 넘음 |
| 오작동률 | 다른 표정의 출력이 0.3을 넘음. 즉 엉뚱한 표정이 움직임 (낮을수록 좋음) |
| 강도 오차 | 보여 준 표정의 출력과 목표 강도의 평균 차이 (가이드 녹화가 있어야 의미가 있음) |
| 점수 | (정확도 + 인식률 + 2 × (100% − 오작동률) + (1 − 강도 오차)) / 5 |
| ms/프레임, MB | 이 PC에서의 트래킹 비용 |

추천 줄에는 ★가 붙습니다. 점수가 가장 높은 모델이고, 0.5점 이내의 모델이 있으면 그중 가장 빠른 모델입니다. 원하는 줄을 고르고 **선택한 모델 적용**을 누르거나(또는 더블클릭) 하면 바로 현재 모델이 됩니다. 모델 파일에 저장되고(이전 파일은 `<이름>.prev.pt`로 보관), 학습 탭의 선택도 바뀌며, 트래킹 중이었다면 새 모델로 다시 시작합니다. CLI: `compare`, `arch`, `loss`.

**부드러움** (실시간 탭, BCE 모델만): BCE 모델의 시그모이드 출력은 0과 1 사이를 확 오가기 쉽습니다. *부드러움*을 올리면(1 = 끔, 최대 4) 출력이 펼쳐져 표정을 서서히 따라갑니다. 출력의 변환 방식만 바꾸므로 재학습이 필요 없고, 1%는 그대로 0, 99%는 그대로 1이 됩니다. 값이 떨리는 경우에는 *스무딩*을 쓰세요.

모델이나 학습 방식을 바꾼 뒤에는 FastCal을 한 번 하세요. 새 모델은 출력 크기가 조금 다를 수 있고, 최대값은 모델마다 다릅니다.

### 검증 정확도
학습은 각 녹화의 마지막 10%(`config.json`의 `validation_split`)를 따로 떼어 두고, 에폭마다 정확도, 인식률, 오작동률, 점수를, 끝에는 성적이 가장 나쁜 클래스를 알려 줍니다. 무작위 프레임이 아니라 각 녹화의 끝부분을 떼는 이유는, 이웃한 프레임끼리 거의 같아서 무작위로 나누면 정확도가 부풀려지기 때문입니다. 그래도 학습 프레임과 같은 세션이라 수치는 낙관적입니다. 절대적인 정확도가 아니라 모델끼리 비교하는 용도로 보세요.

**다른 세션으로 검증** (학습 탭, 기본 꺼짐, `validation_sessions`): 녹화가 2개 이상인 클래스는 그 클래스의 *마지막* 녹화를 통째로 검증용으로 떼어 두고, 나머지 녹화는 전부 학습에 씁니다. 그 녹화를 다른 날이나 헤드셋을 벗었다 다시 쓴 뒤에 만들면, 착용 상태가 바뀌었을 때 모델이 얼마나 버티는지 수치로 볼 수 있습니다. 과적합된 모델이 무너지는 지점이 바로 여기이고, 같은 세션 수치로는 보이지 않습니다. 가장 좋은 에폭 선택과 *모델 비교*도 이 기준으로 고르게 됩니다. 녹화가 하나뿐인 클래스는 계속 녹화 끝부분으로 검증하고, 학습 로그에 그 목록이 나옵니다. 클래스마다 녹화 하나만큼 학습 데이터가 줄어드니, 모델과 설정을 고른 뒤 최종 학습에서는 다시 끄세요.

**과적합 대책** (학습 탭, 둘 다 기본 꺼짐. *다른 세션으로 검증*을 켜고 비교해 보세요):
* **증강 (위치·조명 변화)** (`augment`): 학습 배치마다 피처를 최대 한 칸(카메라 기준 약 5픽셀, 헤드셋이 살짝 다르게 씌워진 것과 비슷) 이동시키고, 크기를 ±10%(조명) 바꾸고, 작은 노이즈를 더합니다. 두 카메라는 따로 움직이므로 눈과 얼굴 피처는 각각 다르게 이동·조정합니다. 검증 프레임에는 적용하지 않습니다. 학습 장치에서 실행되므로 NVIDIA GPU에서는 거의 비용이 없고, CPU 학습은 약 15~40% 느려집니다.
* **가중치 감쇠** (`weight_decay`, 예: 0.05): Adam 대신 AdamW를 씁니다 (0 = 원래 Adam). 감쇠량에 학습률이 곱해지므로, 학습률이 10배 큰 compact 모델에서 주로 효과가 납니다.
* *모델 비교*에서 **선택한 모델마다 증강 버전도 학습**을 체크하면 모델마다 증강 켬/끔을 나란히 비교할 수 있습니다. 행을 적용하면 그 행을 학습할 때 쓴 증강 설정도 함께 적용됩니다.

**증류** (학습 탭, 학습 방식 옆, 기본 꺼짐): lite와 compact 모델은 standard보다 실행 비용이 5~14배 적지만 (compact는 프레임당 0.32ms, standard는 4.5ms로 측정), 작은 모델은 정확도가 떨어질 수 있습니다. 증류를 켜면 먼저 standard *선생* 모델을 학습하고, 작은 모델은 녹화 정답 30%와 선생의 출력 70%로 학습합니다. 선생의 출력은 "웃음 70%, 입 벌림 20%"처럼 부드러운 값이라, 0/1 정답보다 작은 모델에게 프레임마다 더 많은 정보를 줍니다. 학습 시간은 약 2배가 되지만, 트래킹에는 작은 모델만 씁니다. standard 모델에서는 효과가 없습니다. *모델 비교*에서 **증류한 compact + BCE 모델도 학습**을 체크하면 후보로 추가되고, 비교 중에 학습한 standard + BCE 결과를 선생으로 재사용합니다. 내 데이터에서 차이가 좁혀지는지 직접 볼 수 있습니다. 효과는 녹화 데이터에 따라 다릅니다.

**가볍게 유지하기 위한 장치** (모두 측정함):
* 출력을 받는 곳이 없으면(VRCFaceTracking 미연결, OSC 출력 없음) 트래킹이 **10Hz**로 줄고, 무언가 연결되면 0.5초 안에 원래 속도로 돌아옵니다. 실시간 탭은 계속 갱신됩니다.
* 카메라 영상은 미리보기가 보일 때만 복사합니다. 미리보기 확대는 Tk가 처리합니다 (프레임당 9ms 대신 1.6ms). 창을 최소화하면 1초에 한 번만 갱신합니다.
* 프레임마다 실행되는 Python 코드는 숫자 하나에 NumPy를 쓰지 않고, 출력 설정은 0.5초마다만 다시 읽습니다. VRCFT와 OSC 인코딩은 미리 만들어 둡니다.
* 시작할 때는 필요해질 때까지 PyTorch도 ONNX Runtime도 불러오지 않습니다 (import 0.1초, 34MB).
* conv 계층의 정적 int8 양자화도 시험했습니다. 40% 빨랐지만 출력 오차가 약 15%라 쓰지 않습니다.

대기 중인 작업 스레드가 바쁘게 기다리지 않도록 설정해서(`OMP_WAIT_POLICY=PASSIVE`, ONNX Runtime spinning 끔) 프레임 사이에 CPU를 낭비하지 않습니다.

### PyTorch 없는 PC에서 트래킹하기
`config.json`, `buddyguy.onnx`, `buddyguy.int8.onnx`, `buddyguy.json`을 앱 옆에 복사한 뒤 `pip install numpy onnxruntime`을 실행하세요. 트래킹은 PyTorch 없이 동작하고, 학습에만 PyTorch가 필요합니다.

## 6. VRCFaceTracking (설정 탭 → VRCFaceTracking 모듈)
**VRCFaceTracking v6**에서는 앱의 **설치 / 업데이트**로 모듈을 설치한 뒤 VRCFaceTracking을 다시 시작하세요. 상태 표시줄에 *VRCFaceTracking: 연결됨 (v6 모듈)*이 표시됩니다.

* VRCFaceTracking v6는 아이 트래킹과 표정을 각각 모듈 하나만 담당할 수 있어서, Pal Buddy Guy 모듈이 **SRanipal 모듈을 자기 안에서 실행**합니다. 설치 프로그램은 단독 SRanipal 모듈의 `module.json` 이름을 바꿔 비활성화하고, **제거**를 누르면 원래대로 되돌립니다. 먼저 VRCFaceTracking에서 SRanipal 모듈을 설치해 두세요.
* 클래스의 *대상 파라미터*로는 (예전처럼) SRanipal 입 모양이나, SRanipal이 표현하지 못하는 `BrowLowererLeft`, `EyeSquintRight` 같은 눈 주변 표정을 포함한 모든 **Unified Expression**을 고를 수 있습니다. 예를 들어 Pro Eye 카메라로 보이는 찡그림을 학습할 수 있습니다.
* **v1 (레거시 SRanipal) 아바타 파라미터도 동작합니다.** VRCFaceTracking v6는 v1 파라미터(`JawOpen`, `MouthSmileLeft`, `SmileSadLeft`, `JawX` 등)를 Unified Expression에서 계산합니다. SRanipal 대상은 이 변환을 거친 뒤 v1 파라미터가 학습한 값과 **정확히** 같아지도록 변환해서 보내며, 모든 표정에 대해 VRCFaceTracking 자체의 파라미터 함수로 검증했습니다. v1 눈/눈썹 파라미터(`LeftEyeWiden`, `LeftEyeSqueeze`, `BrowDownLeft`, `BrowsInnerUp` 등)도 대상으로 바로 고를 수 있습니다. VRCFaceTracking 자체에서 오는 제한은 다음과 같습니다.
  * v1 `Tongue*Morph` 파라미터는 v6에서 항상 0입니다. Pal Buddy Guy는 대신 두 가지 혀 방향을 움직입니다.
  * `MouthUpperOverturn` / `MouthLowerOverturn`은 v1 `MouthUpperUp*` / `MouthLowerDown*`도 함께 올립니다. VRCFaceTracking의 변환 공식을 따른 것이고, Unified 기반 모듈은 모두 같습니다.
  * `MouthSadLeft/Right`는 `MouthStretch*`로 보냅니다. 그래야 반대쪽으로 새지 않고 v1을 정확히 재현하기 때문입니다. Unified(v2) 아바타라면 대신 `MouthFrownLeft/Right`를 고르세요.
* 기본적으로 Pal Buddy Guy가 움직이는 표정은 SRanipal 값 대신 Pal Buddy Guy 값을 씁니다. *SRanipal 값이 더 크면 유지*를 켜면 둘 중 큰 값을 씁니다.
* 트래킹을 멈추면 모듈이 0.5초 안에 원래 SRanipal로 돌아갑니다.
* 원래 VRCFaceTracking 모듈(v4 이하)도 계속 동작하지만, SRanipal 입 모양만 이해합니다.

## OSC 직접 출력: 병합 파라미터와 클래스 파라미터
VRCFaceTracking 표정을 움직이는 것 외에, 학습한 클래스를 원하는 아바타 파라미터 이름으로 **OSC를 통해 VRChat에 직접** 보낼 수 있습니다 (기본값 127.0.0.1:9000).

* **클래스 파라미터** (학습 탭 → 클래스 → *OSC 파라미터*): 클래스 값, 0~1.
* **병합 파라미터** (병합 파라미터 탭): **클래스 여러 개를 가중치로** 합칩니다. `합계 = Σ 클래스 × 가중치`이고 -1~1로 제한됩니다 (모든 클래스가 0이면 0). 예: `웃음 × 1 + 슬픔 × -1`, 또는 VRCFT의 EyeLidExpandedSqueeze처럼 `넓힘 × 0.2 + 뜸 × 0.8 + 찡그림 × -1`. 합계는 세 점으로 변환됩니다: **-1 → 최소, 0 → 중간값, +1 → 최대**. 프리셋은 -1~1, 0~1, 0~2이고, 최소·최대·**중간값**을 모두 직접 정할 수 있습니다. 예를 들어 0~2에 중간값 1이면 슬픔은 0, 무표정은 1, 웃음은 2가 됩니다.

**형식**: *float*, *바이너리*, *둘 다* 중에서 고르고, 해상도는 1~8비트입니다. 바이너리는 VRCFaceTracking 바이너리 파라미터와 같은 방식입니다. bool 파라미터 `<이름>1`, `<이름>2`, `<이름>4`, …가 `int(값 × 2^비트)`의 *i*번째 비트를 담고, 1에 가까우면 모든 비트가 켜집니다. 그래서 기존 VRCFT 바이너리 애니메이터 설정으로 그대로 해석할 수 있습니다. 0을 가로지르는 범위(예: -1~1)는 `<이름>Negative`를 추가하고 크기를 인코딩합니다. 그 밖의 범위는 범위 안의 위치를 인코딩합니다 (최소 쪽 0, 최대 쪽 1). bool은 값이 바뀔 때만 보내고, 1초마다 전체를 한 번 다시 보냅니다.

**페이셜 트래킹을 방해할 수 있는 이름은 거부됩니다.** VRCFaceTracking은 자기 파라미터와 이름이 같거나 `/<이름>`으로 끝나는 모든 아바타 파라미터를 움직입니다 (그래서 `PBG/SmileSad`는 VRCFT의 `SmileSad`가 움직입니다). 바이너리 비트 `<이름><숫자>`와 `<이름>Negative`도 마찬가지입니다. 앱은 출력이 쓰는 모든 이름을 VRCFaceTracking v6의 v1/v2/눈/머리 파라미터 744개와 바이너리 파라미터 367개(VRCFT 소스에서 생성한 `palbuddy/vrcft_names.py`)와 대조해서, 겹치면 거부합니다. 그래서 이 출력을 쓰지 않거나 `PBG_SmileSad` 같은 이름으로 쓰면 기존 페이셜 트래킹은 전혀 영향을 받지 않습니다. 같은 파라미터를 두 번 쓰는 출력도 거부됩니다. 잘못된 출력이 학습을 막지는 않고, 보내지지 않을 뿐입니다.

트래킹을 멈추면 모든 출력이 중간값으로 돌아갑니다. VRChat은 float 파라미터를 -1~1 범위로 동기화하므로, 그 범위를 벗어나는 값(0~2)은 동기화하지 않는 로컬 파라미터에서만 그대로 전달됩니다. 바이너리 파라미터는 문제없이 동기화됩니다.

CLI: `merged add PBG_SmileSad smile,-sad -1 0 1 binary 4` (항목, 최소, 중간값, 최대, 형식, 비트), `merged add PBG_Lid 0.2*wide,0.8*open,-squeeze 0 0.5 1`, `oscout sad PBG_Sad both 3`, `merged`, `merged remove NAME`. positive/negative 클래스를 쓰던 예전 설정은 항목 두 개로 불러옵니다.

## 민감도 (실시간 탭)
어떤 클래스가 예를 들어 0.2~0.8 사이에서만 움직이면, 그 구간을 다시 0~1로 늘릴 수 있습니다. 출력 목록에서 클래스를 클릭하고 **하한** / **상한**을 조정하세요. 막대 위의 주황색 표시가 그 위치입니다. **자동 (5초)**은 자동으로 측정합니다. 무표정을 지었다가 최대 표정을 지으면, 측정한 값의 5~95 백분위가 범위가 됩니다. 위 막대는 조정 전 값, 아래 막대는 보내는 값입니다. 조정은 VRCFaceTracking 표정과 OSC 출력에 똑같이 적용됩니다. CLI: `sens smile 0.2 0.8`

**무표정 보정** (실시간 탭, FastCal 옆, 5초 걸림): 가만히 있는데 표정 값이 올라간다면 5초 동안 무표정을 유지하세요 (깜빡이거나 두리번거려도 됩니다). neutral을 제외한 모든 클래스의 하한이 그동안 보인 값 바로 위(상위 2% 값 + 0.03)로 맞춰져서, 무표정에서는 0이 나갑니다. 헤드셋을 쓴 뒤에 한 번 하세요. 무표정에서 0.3 이상인 클래스는 따로 알려 줍니다. 모델이 무표정을 그 표정으로 착각하고 있다는 뜻이고, 하한은 그걸 가릴 뿐이라 그 표정의 약한 움직임도 함께 가려집니다. 이런 클래스는 무표정을 다시 녹화해서 (지금, 그리고 다른 날에도) neutral 클래스에 추가하고 다시 학습한 뒤, 보정을 다시 해서 근본적으로 고치세요. CLI: `restcal`

### 안정화와 말하기
말할 때 감정 클래스가 출렁이면 두 가지가 도움이 됩니다.
* **말하기 녹화.** 무표정으로 글을 30초 동안 소리 내어 읽는 녹화를 (다른 세션에서 한 번 더) 만들어서 `neutral`에 넣거나, 더 좋게는 대상 없는 별도 클래스 `talk`로 추가하세요. 그러면 신경망이 말할 때의 입 움직임은 감정이 아니라는 걸 배웁니다. 이것이 근본적인 해결책입니다.
* **안정화** (실시간 탭, 클래스마다, 민감도 슬라이더 아래): 표시된 시간(최대 400ms, 한 음절은 약 100~250ms)보다 짧은 변화를 이동 중앙값과 완만한 저역 통과 필터로 무시합니다. 감정 클래스에 켜고, 말을 따라가야 하는 입 모양에는 끄세요. 계속 유지하는 표정은 조금 늦을 뿐 그대로 반영됩니다.

## 7. 프로세스 우선순위 (설정 탭 → 추론 성능)
트래킹은 CPU를 아주 조금만 쓰므로, 기본적으로 프로세스가 **보통 이하** 우선순위로 실행되어 CPU가 바쁠 때 VR과 게임에 양보합니다. 하이브리드 Intel CPU(12세대 이후, 예: i7-12700K)에서는 **E코어만 사용**으로 P코어를 아예 쓰지 않게 할 수 있습니다. Windows 11에서는 **효율 모드**(EcoQoS)로 스케줄러가 느린 저전력 코어에서 실행하게 할 수 있습니다. *낮음* 우선순위도 있지만, CPU가 꽉 차면 트래킹이 끊길 수 있습니다.

# 원래 스크립트와 달라진 점
**GUI**
* 추가 의존성이 없는 Tkinter GUI: 실시간 연결 상태, 카메라 미리보기, 출력 막대, 진행 표시가 있는 녹화, 클래스/데이터셋 편집, 실시간 손실 그래프와 남은 시간이 표시되는 학습, FastCal, 설정. 영어와 한국어를 지원합니다.

**성능**
* SRanipal을 프록시를 거치지 않고 앱 안에서 직접 받아, TCP 한 단계와 프로세스 하나를 없앴습니다.
* 프레임은 조건 변수가 있는 "최신 샘플 슬롯"으로 전달합니다. 예전 코드는 `pop(0)`을 쓰는 리스트 큐를 1ms sleep 루프로 확인했습니다.
* 추론은 *새* 프레임마다 한 번 실행합니다. 예전 루프는 같은 프레임을 다시 계산하고, 새 프레임이 기다리고 있어도 10ms씩 쉬었습니다. 고정(pinned) 입력 버퍼와 `inference_mode`를 씁니다.
* VRCFT 업데이트는 프레임마다 패킷 하나로 보냅니다. 예전 코드는 Nagle 알고리즘이 켜진 상태로 1 + 3·N번의 작은 `send`를 호출했습니다.
* 학습: 녹화 파일마다 인덱스 읽기 한 번으로 배치를 만들고, GPU가 학습하는 동안 백그라운드 스레드가 다음 배치를 준비합니다. 혼합 정밀도(AMP)와 cudnn 자동 튜닝을 쓸 수 있습니다. 녹화가 `.mmap`에 바로 저장되므로 `pkl → mmap` 변환 단계가 없어졌습니다.
* `batch_size` 전역 변수 편법을 고쳤습니다. 예전에는 추론할 때 이를 1로 바꾸고 dropout 함수를 바꿔치기했습니다.

**연결성**
* 연결 끊김을 감지합니다. 예전에는 상대가 떠난 뒤 `recv()`가 계속 `b""`를 돌려주고, 스레드가 다시 연결하지도 않은 채 CPU를 100% 썼습니다.
* SRanipal이나 VRCFT를 다시 시작하면 오래된 연결을 자동으로 교체합니다. 스크립트를 다시 시작할 필요가 없습니다.
* VRCFT 연결은 TCP_NODELAY와 keepalive를 씁니다. 전송 제한 시간이 있어서 VRCFT가 멈춰도 트래킹이 멈추지 않습니다.
* 모든 포트는 기본적으로 모든 네트워크 인터페이스가 아니라 `127.0.0.1`에서만 수신합니다. 설정으로 바꿀 수 있습니다.
* 포트를 설정할 수 있고, 포트가 이미 사용 중이면 명확한 오류 메시지를 보여 줍니다.
* 프록시 클라이언트(레거시 모드)는 간격을 늘려 가며 다시 연결합니다.
* 상태 표시줄에 각 스트림이 연결됨, 데이터 없음(멈춤), 연결 안 됨 중 어느 상태인지 표시합니다.

기존 신경망 구조(표준), `buddyguy.pt` 체크포인트 형식, 녹화 형식, VRCFT 통신 규약은 그대로라서, 기존 모델, 녹화 파일, VRCFT 모듈을 계속 쓸 수 있습니다.
